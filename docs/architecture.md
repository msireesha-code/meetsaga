# Architecture

## Overview

```
              ┌───────────────────┐
              │   Audio / Video   │
              └─────────┬─────────┘
                        ▼
              ┌───────────────────┐
              │ Media Processing  │  ffprobe metadata + ffmpeg audio extraction
              └─────────┬─────────┘
                        ▼
              ┌───────────────────┐
              │  Transcription    │  Local (faster-whisper) or Remote (HTTP)
              └─────────┬─────────┘
                        ▼
              ┌───────────────────┐
              │ Speaker           │  pyannote.audio — independent, can fail
              │ Diarization       │  without failing the job
              └─────────┬─────────┘
                        ▼
              ┌───────────────────┐
              │ Structured        │  SQLite: Transcript + TranscriptSegment rows
              │ Transcript        │  (the source of truth)
              └─────────┬─────────┘
                        ▼
              ┌───────────────────┐
              │ Meeting           │  OpenAI-compatible LLM — independent, can
              │ Intelligence      │  fail without failing the job or discarding
              └─────────┬─────────┘  the transcript
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
      Summary       Decisions    Action Items  (each keeps source_segment_ids)
          └─────────────┼─────────────┘
                        ▼
              ┌───────────────────┐
              │ Search / Review   │
              │ Export / Insights │
              └───────────────────┘
```

## Frontend

React 18 + TypeScript + Vite, in `frontend/`. No state management library —
each page fetches what it needs from the API directly via `services/api.ts`
(a thin `fetch` wrapper), and polls `/api/jobs` while a job is in flight.
Routing via `react-router-dom`. Pages live in `frontend/src/pages/`,
reusable pieces (transcript/player sync, action-item table, nav) in
`frontend/src/components/`.

## Backend

FastAPI app in `backend/app/`:

```
app/
├── main.py            FastAPI app, CORS, router wiring, startup DB init
├── config.py           Settings (pydantic-settings, reads .env), language/model registries
├── database.py         SQLAlchemy engine/session, init_db()
├── schemas.py           Pydantic request/response models
├── models/entities.py   SQLAlchemy ORM models (see Database Model below)
├── api/                 One router module per resource area
├── services/
│   ├── media/           ffprobe/ffmpeg wrappers + upload validation/sanitization
│   ├── transcription/    Provider abstraction (base.py) + local/remote implementations
│   ├── diarization/      pyannote.audio wrapper
│   ├── analysis/         LLM analyzer abstraction + OpenAI-compatible implementation + chunking
│   └── export/           Format renderers (txt/srt/vtt/json/md)
└── workers/
    └── job_runner.py     Orchestrates the whole pipeline per job
```

## API Architecture

REST endpoints, one router per resource (`api/meetings.py`, `api/jobs.py`,
`api/transcripts.py`, `api/analysis.py`, `api/settings_api.py`, `api/system.py`,
`api/dashboard.py`, `api/search.py`, `api/exports.py`). Interactive docs are
auto-generated by FastAPI at `/docs`. CORS is restricted to the dev frontend
origins (`localhost:5173`) in `main.py` — adjust for a different deployment
(see [deployment.md](deployment.md)).

## Database Model

SQLite via SQLAlchemy, single file (`data/meetsage.db`), schema created with
`Base.metadata.create_all()` at startup (no migration framework — see
[backup-recovery.md](backup-recovery.md) for upgrade implications). Entities:

- **Meeting** — name, original filename, media type, expected languages, duration
- **Media** — original/normalized file paths, ffprobe metadata
- **Job** — one row per processing run (initial run, re-analysis, or
  re-diarization), tracks status/stage/progress/timings/error, references a Meeting
- **Transcript** + **TranscriptSegment** — versioned per meeting; segments carry
  `start`, `end`, `speaker_label`, `language`, `text`
- **Speaker** — per-meeting label → display_name mapping
- **Analysis** + **ActionItem** — versioned per meeting (`is_current` flag), so
  re-running analysis doesn't destroy history
- **RemoteProvider** — remote transcription endpoint configs (token stored, never returned)
- **AppSetting** — key/value store for the runtime-editable Settings UI sections

Action items and decisions/risks/etc. carry `source_segment_ids` (integer
indices into that job's segment list at analysis time) so the UI can link back
to the transcript.

## Filesystem Storage

See [configuration.md](configuration.md#storage-layout). Uploaded files are
renamed to `{meeting_id}_{random}.{ext}` on disk — the user-supplied filename
is sanitized (`services/media/validation.py::sanitize_filename`) and kept only
as a display field, never used to construct a filesystem path.

## Job Processing

`workers/job_runner.py` runs each job on a `ThreadPoolExecutor` sized by
`MAX_CONCURRENT_JOBS` (default 1). A job progresses through:

```
QUEUED → VALIDATING → MEDIA_ANALYSIS → PREPROCESSING → TRANSCRIBING →
DIARIZING → ANALYZING → COMPLETED
```

(`FAILED`/`CANCELLED` are terminal states reachable from most stages.) Two
separate lighter-weight entry points exist for re-running just one stage
without repeating expensive work: `submit_reanalysis_job` (ANALYZING only,
against the latest transcript) and `submit_rediarization_job` (DIARIZING only).

**Fault tolerance is a deliberate design choice, not an oversight**: a
diarization failure or an analysis failure marks the *stage* as failed
(recorded in `job.error`) but the job still reaches `COMPLETED` if
transcription succeeded — the transcript is never discarded because a
downstream, independent stage failed. This was verified against real failures
during development (HuggingFace license gating, a pyannote-audio API change,
and a missing LLM key) — see `backend/tests/test_job_pipeline.py`.

Transcription progress is reported as an honest fraction of audio duration
actually processed (via a callback from `faster-whisper`'s segment generator),
not a fabricated estimate — the API doesn't provide finer-grained progress
than that.

## Provider Abstraction

```python
class TranscriptionProvider(ABC):
    def transcribe(self, audio_path, expected_languages, auto_detect_languages,
                    progress_callback=None) -> TranscriptionResult: ...
```

Two implementations: `LocalTranscriptionProvider` (faster-whisper) and
`RemoteTranscriptionProvider` (HTTP call to an OpenAI-compatible
`/v1/audio/transcriptions` endpoint — always made backend-side, never from the
browser). `services/transcription/registry.py::build_provider` is the single
factory the rest of the app uses; no other module imports a concrete provider
class. Adding a new provider means adding one class here — see
[development.md](development.md#adding-a-transcription-provider).

Analysis follows the same pattern: `MeetingAnalyzer` ABC in
`services/analysis/base.py`, currently one implementation
(`OpenAICompatibleAnalyzer`) that works with any compatible endpoint by
configuration, not by provider-specific code branches.

## Multilingual Transcription

`faster-whisper` is run with `language=None` (always auto-detect — the
transcript is never forced into one language) and, when the meeting has more
than one expected language, `multilingual=True`, which makes Whisper re-check
language per ~30-second internal window rather than once for the whole file.

**Important limitation**: faster-whisper's public API does not expose a
per-segment language label even with `multilingual=True` — that internal
re-detection isn't surfaced per output segment. So MeetSage tags each segment
itself, in `services/transcription/language_id.py::detect_segment_language`,
using **Unicode script detection**: it counts Devanagari, Telugu, and Latin
characters in the segment's actual text and reports the dominant script. This
is deterministic and derived only from what Whisper already transcribed — it
never alters the transcript text itself. For a genuinely code-switched segment
(English words inside an otherwise Hindi sentence), this reports the
*dominant* language, not per-word attribution. This is documented, not hidden,
because it directly affects how much to trust the `language` tag on any given
segment — see [troubleshooting.md](troubleshooting.md#mixed-language-transcription-problems).

## Diarization

`services/diarization/pyannote_provider.py` loads
`pyannote/speaker-diarization-3.1` via `Pipeline.from_pretrained(...,
token=HUGGINGFACE_TOKEN)`, lazily and cached per-process. Audio is loaded with
`soundfile` and passed as a `{"waveform": tensor, "sample_rate": int}` dict
directly — deliberately bypassing `torchcodec`, which failed to load its
native extension in this environment (see
[troubleshooting.md](troubleshooting.md#diarization-failure)). Output is
matched against transcript segments by maximum temporal overlap
(`assign_speakers_to_segments`); a segment with no overlapping speaker turn is
left unassigned rather than guessed.

pyannote-audio 4.x wraps its pipeline output in a `DiarizeOutput` dataclass
(`.speaker_diarization` holds the `Annotation`); the code handles both that and
the older versions' raw `Annotation` return, via
`getattr(diarization, "speaker_diarization", diarization)`, so a future
pyannote upgrade degrades gracefully instead of crashing.

## Analysis

`services/analysis/openai_compatible.py`: transcript segments are chunked by a
character budget (`services/analysis/chunking.py`, ~12,000 chars/chunk,
splitting only between segments so none is cut mid-sentence). Each chunk is
analyzed independently via one LLM call with a strict system prompt (never
invent an owner/date/priority; every extracted item must cite
`source_segment_ids`). If there's more than one chunk, a final synthesis call
merges only the **summary** into one coherent narrative; every other
list-type field (decisions, action items, open issues, risks, dates,
questions) is concatenated directly from the per-chunk results rather than
re-generated — this guarantees nothing found in one chunk is silently dropped
by a synthesis pass (spec requirement for long meetings).

## Export

`services/export/formats.py` — pure functions, no I/O, taking plain dicts (not
ORM objects) so they're independently unit-testable. `api/exports.py` resolves
each segment's speaker label against any renamed `Speaker.display_name` before
formatting, so exports reflect renames.

## Error Handling

Every stage failure is caught, attached to the job's `error` field, and
classified as retryable or not (`TranscriptionProviderError.retryable`,
`AnalysisError.retryable`). Errors are shown on the Jobs page. Secrets
(API tokens, `Authorization` headers, HuggingFace tokens) are redacted from
logs by a regex-based logging filter (`app/logging_config.py`) as
defense-in-depth, in addition to simply never logging them in the first place.
